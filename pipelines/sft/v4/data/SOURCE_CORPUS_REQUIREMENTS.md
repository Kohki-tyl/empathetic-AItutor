# v4コーパス要件

## 1. 目的

v4は、日本語数学チューターの教師役を対象とするKeep-only SFTコーパスである。SFTで同時に改善する対象は次の二つとする。

1. 生徒の理解済み事項、誤概念、つまずき、感情、必要な支援量を発話根拠から推定する認知的・情緒的共感
2. 推定結果を、数学的に正しい正誤判定、一段階の足場かけ、支援変更、理解確認へ変換する数学的指導

共感表現の増加、直接解答の抑制、シミュレータ内部の理解度上昇だけを成果としない。誤答追認を防ぎ、生徒が未知の問題で自力解決へ近づく教師行動を学習対象とする。

## 2. 問題と候補の要件

- 問題源は`translated_1000_math.jsonl`とする。
- `math_train_0`から数値順に扱う。問題選定LLMは使用しない。
- 先頭800問をコーパス候補、後半200問をテスト専用候補とし、両者の問題IDを重複させない。
- `mastered`、`frontier`、`one_step_beyond`、`far_beyond`を各30件、seed 42で固定抽出し、生成候補を120件とする。
- 生成目標は100対話、最大指導ターンは1対話10教師ターンとする。ただし、監査を通過した候補を100件で切り捨てず、追加の高品質対話は由来を記録して保持できる。
- コーパス作成時にはtrain/validationへ分割しない。分割はSFT工程で行う。

## 3. 問題・プロフィール対応要件

- 問題ID、問題本文hash、問題分野、必要教育課程、プロフィール、範囲関係、初期感情、誤概念を事前対応表へ保存する。
- 8種類のE2/E3プロフィールを使用し、`prior_knowledge`を開始時に自力使用できる知識の完全な一覧とする。
- `mastered`では条件確認や検算が一部不足した回答、`frontier`では分野固有の誤概念または部分手続き、範囲外では援助要請を初回応答の中心とする。
- `one_step_beyond`と`far_beyond`では初回応答を`scope_limited_help_seeking`へ固定する。
- `far_beyond`では、異なる2回の既習範囲内の試行、各停止位置、共通の停止箇所を事前に与え、初回生徒発話の先頭で明示する。
- 問題難度のMATH `level`を学校段階として解釈しない。教育課程段階は問題・解答の概念から別途推定する。

## 4. 生徒シミュレータ要件

- 生徒モデルは`gpt-5.4-mini`、Chat Completions、Structured Outputs、reasoning effort `none`を使用する。
- 教師モデルと生徒モデルを共有しない。
- 初期感情はプロフィールと分離し、問題範囲との差と難度から事前決定する。
- 初回発話では初期感情、理解度、誤概念、獲得知識を教師介入前に変更しない。
- 感情変化は定義済みサイクル内の一段階以内、理解度変化は1ターン一段階以内とする。
- 発話では感情ラベルや内部状態名を直接述べず、語調、ためらい、確信度、発話量に反映する。
- `knowledge_used`は既習知識、直前までの獲得知識、そのターンで教師が導入した知識の範囲内とする。
- プロフィールより明らかに賢い回答、未導入公式の突然の使用、教師役への逸脱を許容しない。

## 5. 教師生成要件

- 教師モデルは`gpt-5.6-terra`、Chat Completions、reasoning effort `high`を使用する。
- 教師は初回入力で問題、内部検算用参照解答、学習範囲、初期感情、試行履歴、生徒発話を受け取る。2ターン目以降は対話履歴と最新生徒発話から状態を推定し、現在感情ラベルを外部入力として受け取らない。
- 内部出力を次の5ブロックとする。
  1. `mathematical_assessment`
  2. `learner_state`
  3. `support_decision`
  4. `is_completed`
  5. `teacher_utterance`
- 内部では感情受容文を作る前に、生徒回答、参照解答、教師が提示する数学を独立に検算する。
- 生徒向け発話は原則「具体的な受容→数学的正誤→一つの問いまたはヒント」の3文とし、強い不安・フラストレーションまたは必要な補足がある場合だけ4文とする。
- 一度に扱う新しい内容は一つとし、不必要な完成解答、同じ問いの反復、根拠のない規則提示を避ける。
- 理由または主要途中式を確認した場合だけ`is_completed=true`とする。完了時は追加質問を出さず、`next_support`と`change_reason`を「なし」にする。

## 6. 生成時の構造要件

- 生徒・教師ともStructured Outputsのschemaを満たす。
- 生徒と教師のroleを交互にし、ターンの追加、欠落、重複を認めない。
- 生徒表面発話と教師表面発話は非空で、JSON、内部状態、予約marker、ANSI escape、NULを含む制御文字を含めない。
- 教師の内部検算と`teacher_utterance`を矛盾させない。
- 後続生徒の獲得知識が直前教師発話から取得された場合、対応する知識表現を教師発話に保持する。
- 生成検証は生徒・教師とも最大3回再試行し、失敗した出力本体と理由を診断ログへ残す。

## 7. 監査項目

対話全体を次の6項目で各10点評価する。

| 評価項目 | 要件 |
|---|---|
| 数学的正確性 | 生徒と教師の式、計算、定義、結論が正しい |
| 誤りの診断と回復 | 正答・部分正答・誤答・誤概念を区別し、回復へ導く |
| 認知的共感 | 理解・つまずき・必要支援量を発話根拠から推定する |
| 感情認識・情緒的支援 | 感情を根拠付きで推定し、安全で課題に接続した受容を行う |
| 適応的足場かけ | 自力で越えられる一歩を示し、停滞時に方法を変更する |
| 理解確認・完了判定 | 理由または主要途中式を確認してから完了する |

合計点で低い項目を相殺しない。誤答追認、教師の数学的誤り、内部検証と発話の矛盾、根拠のない完了、問題外への誘導、内部分析の露出をCritical failureとする。

## 8. Keep要件

### 8.1 通常Keep

次をすべて満たす。

- 6項目が各8点以上
- 数学的正確性、生徒回答判定、認知・感情推定、状態更新、プロフィール、役割、初期感情、完了判断が妥当
- 分析が受容、正誤説明、問い、ヒント、説明量または支援変更へ反映される
- 誤答追認、不必要な直接解答、Critical failureがない
- `issues`と`repair_instructions`が空
- 後述するSFT構造ゲートを通過する

### 8.2 採択可能な未完了

次のいずれかだけを理由に非Keepとしない。

- 最大10教師ターン以内に最終解、検算、生徒自身の理由説明へ到達しない
- 高難度問題を正確かつ共感的に細かく支援した結果、問題全体へ戻る前に上限へ到達する

この例外では、数学的正確性、誤りの診断と回復、認知的共感、感情認識・情緒的支援を各8点以上とし、数学・状態推定に関する必須booleanを満たし、誤答追認、直接解答、Critical failure、未解決issues、repair instructionsがないことを要求する。`acceptable_incompleteness`へ理由を明示する。完了不足そのものに対応する適応的足場かけまたは理解確認の点数だけは8点未満になりうる。

数学的誤り、誤答判定、根拠のない規則、局所的にも進まない支援、未確認の完了宣言は、この例外では許容しない。

## 9. Repair・Reject要件

- 教師内容の問題は、問題、生徒発話、対象外教師発話を固定したまま、前後の文脈に両立する教師発話へ修正できる場合だけRepairとする。
- Repairは対話全体と監査結果を入力し、必要な教師ターンをまとめて修正する。
- Repair後は修正箇所だけでなく対話全体を同じ60点基準で再監査し、Keepだけを採択する。
- 表面発話の制御文字・空発話はLLM judgeのKeep判定より構造ゲートを優先する。破損文字列だけを、役割、内部状態、知識水準、前後発話を固定して最小限に復元し、対話全体を再監査する。
- 生徒の意味内容、知識水準、感情、役割を修正しなければ成立しない場合はRejectとする。
- 最新の完了済み監査だけを採択判定へ使用し、古いKeep・Repair判定を混在させない。

## 10. SFT構造ゲート

LLM judgeがKeepでも、次のいずれかがあればSFTへ含めない。

- 生徒または教師の表面発話に制御文字、ANSI escape、予約markerがある
- 生徒または教師の表面発話が空、または制御文字を除くと空になる
- roleが`system → user → assistant`以降交互でない
- candidate IDが重複する
- 教師構造化判断の必須fieldが欠ける
- 修正後の最新全体監査がKeepでない

内部メタデータの軽微な更新漏れは`metadata_warnings`へ分離し、教師SFTに直接含まれない場合はそれだけで除外しない。ただし、生徒モデルの学習データには使用しない。

## 11. SFT形式

- 1対話を1件のmessages JSONLとする。
- 最初の`user`へ問題、初期感情ラベル、最初の生徒発話を含める。現在感情は毎ターン入力しない。
- `assistant`は短い明示的判断記録を`<analysis>`、生徒向け発話を`<final>`へ格納する。
- `is_completed=true`のassistantだけに変換処理で`[指導完了]`を付ける。
- systemとuserをloss maskし、assistant-only lossとする。analysisとfinalは両方を学習対象とする。
- 対象モデル固有のchat templateを使い、特殊tokenを手作業で追加しない。
- 対象tokenizerで全件の長さを監査し、assistant targetを途中で切らない。暗黙の右側truncationは禁止する。
- 上限超過時は教師ターン境界で分割し、system、問題、必要な直近履歴を保持する。

## 12. 構成・再現性要件

- profile、初期感情、scope relation、完了・未完了、未完了理由、選択経路、教師感情、支援変更の分布を記録する。
- 不足条件を既存ラベルの書き換えで補わず、候補追加で対応する。
- モデル名、reasoning effort、provider、SDK版、seed、設定、問題・対応表・選択表・プロンプトのSHA-256、run fingerprintをmanifestへ保存する。
- API処理は1件ずつ結果を追記し、完了済みcandidate IDから再開できるようにする。
- Repair、再監査、表面修正の履歴を残し、最終コーパスでは各candidate IDの採択経路と採択に使った最新監査を追跡できるようにする。

## 13. 現在の成果物に対する判定

- 初回Keep 81件と教師Repair後Keep 24件を統合した105件を、全Keep候補コーパスとして保持する。
- 表面破損18件を修正・全体再監査した結果、17件を追加可能、1件を保留とする。
- 現時点のSFT構造ゲート通過数は104件である。
- 生成・Repair・監査に同じ教師モデル系列を使用しているため、スコアにはjudge適合が含まれうる。ABCIでのSFT前に、別モデルまたは人手による層化抜き取り監査と対象tokenizerによる長さ監査を行う。
